Chapter 1: Problem Definition

The Exact Application: Heterogeneous Corporate Data Harmonization

Modern enterprise data ecosystems suffer from fragmented corporate identity records across departmental silos. This platform ingests multi-source un-keyed datasets, resolves ambiguous entity duplicates using deterministic and fuzzy graph algorithms, and outputs an ACID-compliant Apache Iceberg Lakehouse table alongside a production ML revenue prediction model.

Source S1: Supply Chain Records

Ingested from supply_chain_data_s1.csv (1,200 rows). Contains operational procurement data, vendor logistics, delivery delay scores, and purchase order volumes.

  • Dirty Data Attributes: Inconsistent legal company names (e.g. Apex Logistics Inc. vs Apex Logistics Corporation).
  • Tax Identifier Format: Formatted hyphenated EINs (e.g. 12-3456789) with sporadic missing entries.
  • Operational Metrics: Inventory turn rate, delivery lead times, supplier credit tier.
Volume: 1,200 Records Header Schema: Operational / Logistics

Source S2: Financial & Credit Records

Ingested from financial_data_s2.csv (1,200 rows). Contains balance sheet accounts, audited revenue figures, tax filings, and institutional risk metrics.

  • Dirty Data Attributes: Entity name abbreviations and aliases (e.g. Apex Logistics Group).
  • Tax Identifier Format: Raw 9-digit integers (e.g. 123456789) and conflicting jurisdiction codes.
  • Financial Metrics: Audited annual revenue, EBITDA margins, credit ratings, employee headcount.
Volume: 1,200 Records Header Schema: Financial / Risk

Why Standard SQL Joins Fail on Real Corporate Data

Join Strategy Example Query Attempt Failure Rate Root Cause of Failure
Exact Tax ID Match ON s1.tax_id = s2.ein 38.4% Missed Formatting discrepancies (12-3456789 vs 123456789) + null/unregistered foreign tax IDs.
Exact Name Match ON LOWER(s1.name) = LOWER(s2.name) 61.7% Missed Legal suffixes (Inc, LLC, Corp, Holdings), typographical noise, punctuation.
Unfiltered Fuzzy Match Levenshtein(s1.name, s2.name) < 4 22.1% False Positives Disastrously merges distinct corporate subsidiaries (e.g. Apex Logistics US and Apex Logistics UK).
Our 3-Tier Multi-Attribute Engine Exact Tax ID + Token Levenshtein (≥ 0.88) + Country + Year < 0.2% Error Corroborates Tax ID with normalized name similarity, jurisdiction, and founding date. Isolates ambiguous rows to Quarantine.

The 3-Tier Entity Resolution Engine Architecture

Tier 1: Deterministic Tax ID Match

Both S1 and S2 tax identifiers are stripped of punctuation, whitespace, and leading zeros, casting into standardized 9-digit strings. Records sharing identical valid tax IDs are instantly linked with 1.00 Match Confidence.

Match Confidence: 1.00 (Exact)

Tier 2: Token-Sort Fuzzy Match

For records lacking direct tax ID matches, names are normalized (lowercase, legal suffix stripping). The engine computes normalized Levenshtein / Jaro-Winkler ratio requiring Similarity ≥ 0.88, matching country code, and founded year $|\Delta| \le 1$.

Match Confidence: 0.92 (Fuzzy Corroborated)

Tier 3: Ambiguity Quarantine

If similarity falls between 0.65 and 0.88, or if name similarity is high but country/founded year conflict, the record is flagged as ambiguous and routed to an isolated S3 audit quarantine path (711 records quarantined) to prevent lakehouse pollution.

Quarantine Count: 711 Records

The 3 Critical Engineering Fixes Applied

1. The 4Gi /dev/shm Shared Memory Fix

The Problem: By default, Docker and Kubernetes allocate a tiny 64 MB to /dev/shm. Ray's Plasma Object Store relies on POSIX shared memory for zero-copy Apache Arrow data deserialization. Without modification, large DataFrame transfers crash instantly with fatal SIGBUS: Bus error.

ray-cluster.yaml 
# tmpfs volume backed by host RAM
volumes:
  - name: dshm
    emptyDir:
      medium: Memory
      sizeLimit: 4Gi

Prevents Plasma memory mapping bus errors across all worker nodes.

2. Object Store Memory Limit (3.6 GiB)

The Problem: If Ray starts without explicit memory boundaries, it attempts to claim 30% of total host RAM for Plasma, causing Kubernetes container cgroups to trigger OOMKilled (Exit Code 137) when Python heap consumption spikes during XGBoost model fitting.

rayStartParams 
# Exactly 3.6 GiB for Arrow objects
rayStartParams:
  object-store-memory: "3865470566"
  block: "true"

Guarantees 8.4 GiB of remaining pod RAM for Python heap execution.

3. Stateful Actor Slot Placement

The Problem: The EntityResolver actor maintains an in-memory graph index of canonical tax IDs and normalized company names. If multiple actor instances were spawned across multiple worker nodes, the entity graph would fragment, producing split-brain canonical IDs.

entity_resolver.py 
# Pinned single-instance placement
@ray.remote(resources={
    "entity_resolver_slot": 1
})
class RayEntityResolver(...):

Enforces single-instance state consistency across all worker tasks.

Chapter 4: Infrastructure as Code

Terraform Configuration: 6-Layer Modular Architecture

Why did we decompose the infrastructure into 6 distinct Terraform modules instead of a monolithic state file? Analyzing the architectural benefits of blast radius containment, state locking isolation, and team privilege separation.

1. Blast Radius Containment

In a monolithic Terraform state, an accidental syntax error or quota failure in an EKS worker pool upgrade risks tearing down VPC subnets, NAT gateways, or dropping S3 lakehouse metadata. Modularization guarantees zero cross-layer destruction.

2. Independent State Locking

Each layer maintains its own distinct S3 state file and DynamoDB state lock. Data engineers deploying new Glue tables or DynamoDB tables never block platform engineers deploying Helm charts or updating Karpenter nodepools.

3. Least-Privilege IAM

CI/CD pipelines assume role-specific credentials per layer: the Networking role only possesses EC2/VPC permissions; the Data role cannot touch Kubernetes clusters; and the EKS role cannot delete S3 lakehouse buckets.

Chapter 9: Security & Telemetry

Zero-Trust Identity, Data Governance & Full-Stack Observability

Implementing strict least-privilege IAM roles via EKS IRSA and AWS Lambda execution roles, end-to-end cryptographic encryption with AWS KMS, and unified Prometheus + Grafana telemetry.

1. IRSA & Zero Static Secrets

IAM Roles for Service Accounts (IRSA) eliminates hardcoded AWS access keys. Pods exchange Kubernetes ServiceAccount tokens via AWS STS OIDC federation to obtain temporary 15-minute scoped IAM credentials.

Zero Static Credentials

2. Cryptographic Envelopes (KMS)

All S3 lakehouse objects, DynamoDB ledger tables, and CloudWatch log streams are encrypted at rest with an AWS KMS Customer Managed Key (CMK) featuring automatic annual key rotation and TLS 1.3 in transit.

KMS CMK AES-256

Ray Head metrics exporter (port 8080) scraped every 15s by Prometheus. Grafana dashboards visualize Ray cluster memory, actor execution throughput, Karpenter spot node consolidation, and CloudWatch structured logs.
